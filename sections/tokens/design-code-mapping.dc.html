Correspondencia diseño y código

Cómo viaja un token hasta el código: la librería lo aplica con mixins Sass y las apps con clases utilitarias.

Formato de tokens

Formato W3C Design Tokens Community Group (DTCG), JSON con $value y $type. Los semánticos apuntan a los primitivos con llaves. En este repositorio no se genera ningún archivo de tokens.

{
  "color": {
    "brand": { "600": { "$type": "color", "$value": "#00698C" } },
    "action": {
      "primary": { "$type": "color", "$value": "{color.brand.600}" }
    }
  }
}

Ejemplo

// _mixins.scss · librería: solo semánticos
@mixin t-body { font: var(--ds-type-body); color: var(--ds-color-text-body); }
@mixin bg-surface { background: var(--ds-color-bg-surface); }

// InlineAlert.scss · componente de la librería
.dsm-alert__text { @include t-body; }

// utilities.scss → utilities.css · una clase por mixin
.t-body { @include t-body; }
.bg-surface { @include bg-surface; }
<!-- template de una app -->
<section class="stack gap-3 p-4 bg-surface r-md">
  <p class="t-body">Texto propio de la app</p>
  <ds-button variant="primary">Continuar</ds-button>  <!-- sin clases utilitarias -->
</section>

Reglas

  1. Los mixins leen variables CSS, no variables Sass: el valor se resuelve en el navegador y un tema solo cambia variables.
  2. Una clase utilitaria existe solo si existe su mixin, y un mixin solo si lo usa un componente o una app.
  3. Una app no aplica clases utilitarias a un componente de la librería. Si necesita otra apariencia, pide una variante del componente.
  4. La librería de referencia de este repositorio (components/) no usa Sass porque el repo no tiene build: cada componente inyecta el CSS ya resuelto, el mismo que daría el @include.
